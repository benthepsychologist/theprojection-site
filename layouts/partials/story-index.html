{{/* story-index.html — the lookup tables behind the site's link policy, built ONCE per build and reused by every bullet. See story-link.html for the policy itself. WHY THIS EXISTS (Ben, 2026-08-11): a feed bullet is a STORY, synthesized from multiple sources — it is never "a link to one source." So a bullet's text must resolve to the thread that carries the story (where the timeline lists every source), not to whichever single article the curator cited. WHY THE PREVIOUS FIX (2026-08-07) DIDN'T HOLD: it looked bullets up in `site.Data.payload.items` — but render_read.py windows the payload to the CURRENT Mon–Sun week. On 2026-08-11 that payload held exactly 3 items against ~40 briefing bullets, so nearly every lookup missed and fell through to the external-link fallback. Right idea, almost-empty table. WHAT THIS USES INSTEAD: every scope's own `news` array in readouts.json — 451 items across 155 scopes, 428 of them thread-tagged, and NOT week-gated. Returns two MAPS, deliberately, not slices: .urls external url → thread slug .pages thread slug → true (only slugs with a published page) Maps because the first version of this returned a flat slice and had story-link.html run a linear `where` over it plus a `site.GetPage` per bullet — ~1,135 bullets sitewide, each rescanning 428 items. Honesty about why, since this comment first claimed otherwise: that version was NOT measurably slower. Timed builds came out at 1m45s before any of this work, 1m48s with the slice version, and 1m50s with these maps — all within noise, because the build is dominated by rendering ~155 scope pages against large JSON data, not by this lookup. The maps are kept because they are O(1) and won't degrade as the corpus grows, not because they fixed a regression. There was no regression. */}} {{ $urls := dict }} {{ range $scope, $r := site.Data.readouts.readouts }} {{ range (or $r.news slice) }} {{ if and .url .threads }} {{ $urls = merge $urls (dict .url (index .threads 0)) }} {{ end }} {{ end }} {{ end }} {{/* url -> STORY id (Ben, 2026-08-11). A story is one event with many witnesses; a thread is the arc containing it. Clicking a bullet about Nvidia's $500B platform should land on that event, not on the multi-week financing narrative — which was the "non-intuitive UX leap" he hit. Built from data/stories.json's own source urls, so a bullet resolves to the story that CITES the same article. This map is consulted BEFORE the thread map in story-link.html, so a thread link is now the fallback rather than the destination. Where a story cites several sources, each of its urls points at it. */}} {{ $stories := dict }} {{ range site.Data.stories }} {{ $sid := .id }} {{ range (or .sources slice) }} {{ if and .url (not .redirect) }} {{ $stories = merge $stories (dict .url $sid) }} {{ end }} {{ end }} {{ end }} {{/* The published-page set, so a thread slug that never got a page renders as plain text rather than a 404 — same intent as the site.GetPage guard this replaces, but computed once instead of per bullet. */}} {{ $pages := dict }} {{ range where site.RegularPages "Section" "threads" }} {{ $pages = merge $pages (dict .File.ContentBaseName true) }} {{ end }} {{ return (dict "urls" $urls "pages" $pages "stories" $stories) }}
